## 질문목록

Q1.
혹시 번역에 대한 리소스는 별도로 생각해야겠지만 서비스에서 I/O를 영어로 번역해서 api 호출하는 형식으로도 토큰 절감 효과를 볼 수 있을까요?

A1.
프롬프트는 무조건 영어로 출력은 한국어로 무조건 모델이 처음부터 중간 산출물까진 영어로 하고 최종 사용자 제공엔 한글로 하는 방법도 있을 수 있음.
사실 절약을 위해선 토큰 최적화를 생각하는게 나을 것 같음


Q2.
산출물 성능을 높이는데 있어서 Agent 워크 플로우를 잘 설계하는 것이 중요한가요, 아니면 프롬프트 엔지니어링을 고도화하는게 더 중요한가요?

A2.
응답 속도에 따라 다르다. (Case By Case)

빠르게 응답을 해줘야하는 서비스의 경우 프롬프트 엔지니어링으로 해결할 수 있고,
응답이 늦더라도 정확도와 같은 것들이 중요할 경우 Agent 워크 플로우로 해결할 수 있을 것 같다.


Q3.
LLM이 일관된 답을 줘야한다는 규제가 있을 때에는 어떻게 해야 하는가?

A3.
일관된 답을 줘야한다는거 자체가 LLM 도입을 재고해볼 필요가 있다.

Q7.

Q9.
RAG도 계속 문서가 추가되면 그 문서 카테고리마다 output이 출력되도록 라인즐 짜게 될텐데
그럼에도 파인튜닝보다 개발 비용대비 효과가 좋은지?

A9.
문서가 계속 추가될 때 별도의 모델 재학습 없이 검색 시스템과 프롬프트 엔지니어링으로 결과 맞춤이 가능해 실시간 업데이트와 빠른 반영에 유리함.


Q10.
벡터디비 종류에 따라 유사도 성능이 달라지는지?

A10.
각 벡터DB는 색인 알고리즘(HNSW, PQ, LSH)과 벡터 비교 방식(코사인 유사도, 내적, 유클리디안 거리), 하드웨어 최적화(SSD 활용, 병렬처리) 등
차이가 있기 때문에 유사도 검색 성능 또한 분명하게 달라짐


Q11.
임베딩은 사실상 index를 위한 HNSW 같은 모델을 계산할 때 사용하는게 목적인지?

A11.
미리 임베딩 후 벡터 스토어에 저장해두면 저장된 벡터들간의 연산만 진행되면 되기 때문에 성능상 이슈를 얻을 수 있다.
본인 또한 아직도 어려워하는 부분이다.

bge-m3 같은 범용모델이 특정 도메인 지식(ex. 쇼핑)이 많이 없다면 rag시 검색도 잘 안될거 같은데, 이런 문제는 어떻게 해결하는지?
